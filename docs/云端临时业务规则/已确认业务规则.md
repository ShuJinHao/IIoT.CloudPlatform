# 云端已确认临时业务规则

## 1. 文档定位

- 本文记录人员与权限、工序与设备、配方、客户端发布与状态、生产数据与过站、AI 只读接口在本轮沟通中已经确认的业务口径。
- 本文是并行修改期间的临时记录，不替代 `../云端规则.md`，也不表示当前源码已经符合这些规则。
- 后续统一治理时，应逐条对照源码、正式规则和受影响测试，将仍有效的结论合并到唯一正式规则入口；完成后删除本临时目录。

## 2. 人员、账号与密码

- 人员档案与身份账号是一体业务。人员入职必须同时创建 `Employee` 和 `IdentityAccount`，二者使用同一个业务 ID。
- 系统只有一个正式 Admin 管理员账号。该账号不得通过普通人员管理流程被停用、终止、重置密码、修改角色或降级。
- 非 Admin 不得对 Admin 执行人员资料、状态、密码、角色、设备范围或个人权限变更。
- 所有人员只能通过“修改自己的密码”入口修改本人密码。
- 唯一 Admin 可以重置普通账号密码；任何人都不能通过“重置他人密码”入口重置 Admin 密码，Admin 只能修改自己的密码。
- 管理员重置普通账号密码不得隐式清除账号 lockout；解锁必须是独立、明确并可审计的操作。

## 3. 权限模型与职责边界

- 普通人员执行设备相关业务时，必须同时满足功能权限和设备数据范围，二者缺一不可。
- 人员设备范围只按 `DeviceId` 直接授权，不建立人员到工序的直接授权，不因获得某工序而自动继承该工序下的全部设备。
- 权限只能从系统正式权限清单中选择，不允许客户端或接口写入任意权限字符串。
- 个人特批权限是例外机制，只能由唯一 Admin 维护。
- RoleAdmin 只能定义和维护非 Admin 角色及其白名单内权限，不能修改 Admin 角色、维护个人特批权限或绕过正式权限清单。
- HrAdmin 只能管理普通人员，具体包括：
  - 人员入职和基础资料维护。
  - 停用和重新启用普通人员。
  - 为普通人员分配已有的非 Admin 角色。
  - 为普通人员维护设备访问范围。
- HrAdmin 不得定义角色、修改角色包含的权限、维护个人特批权限、永久终止人员或操作 Admin。
- 普通人员不得修改本人或他人的角色、功能权限及设备范围。
- 普通人员的永久终止和硬删除只能由唯一 Admin 执行。

## 4. 停用与会话失效

- 普通人员被停用后，账号和人员状态必须在同一业务操作中同步停用。
- 停用必须立即使该人员当前访问令牌、刷新令牌和登录会话失效，不能等已有令牌自然过期。
- 停用后的任何新请求都必须被拒绝；重新启用后必须重新登录，不得恢复使用停用前的会话。
- 永久终止同样必须立即失效全部身份会话，并清理该人员的设备授权。

## 5. HrAdmin 设备授权

- HrAdmin 必须能够取得设备授权所需的候选设备列表。
- 该列表只返回授权操作需要的最小设备标识和展示信息，不等同于授予 HrAdmin `Device.Read` 或全部设备业务数据访问权。
- 设备授权采用完整集合语义：保存时以本次提交的 DeviceId 集合作为最终结果，新增缺少项、删除已移除项；空集合表示清空全部设备授权。
- 候选设备 ID 必须来自正式设备存储，保存前必须校验设备真实存在。

## 6. 工序与设备

- 新设备注册只能由唯一 Admin 执行。
- 设备级联硬删除只能由唯一 Admin 执行，并同时要求 `Device.Delete` 和 `Device.CascadeDelete`。
- 设备删除前必须展示完整影响范围并二次确认；删除和各类级联数量必须进入结构化审计。
- DeviceAdmin 只能在同时具备功能权限和设备范围时查看、维护已授权设备，不得注册或删除设备。
- `ClientCode` 由 Cloud 生成，只用于 bootstrap 和设备寻址，不得人工修改。
- `DeviceId` 是设备正式业务身份，设备名称只用于展示。
- 设备注册时必须选择一个已存在的工序。
- 设备所属 `ProcessId` 注册后不可通过普通设备编辑接口修改；如未来确需迁移，必须另行设计独立的高风险迁移流程。
- 设备普通维护只允许修改展示名称，不允许修改 `ClientCode` 或所属工序。

## 7. 本轮尚未确认为长期口径的事项

- 工序主数据创建、修改和删除是否全部限定为 Admin。
- 新设备注册后 BootstrapSecret 应在注册时生成，还是继续在生成安装包时生成或轮换。
- 工序编码是否应采用大小写不敏感的唯一规则。
- RoleAdmin 内置模板、权限模板播种和权限移除的最终治理方式。

## 8. 配方当前逻辑备案

- 配方目前没有投入实际使用。本节只记录当前源码逻辑，供未来启用配方时重新梳理，不代表已经确认最终配方业务设计。
- 每个配方同时归属于一个工序和一台设备；创建时必须校验工序、设备及二者关系。
- 新建配方的初始版本为 `V1.0`，状态为 `Active`。
- 配方升级不得原地覆盖当前版本，而是归档原有活动版本并创建新的版本记录；正常版本升级应保留旧版本历史。
- 当前状态包括 `Active` 和 `Archived`。Edge 侧只获取 `Active` 配方。
- 当前参数结构主要记录参数标识、名称、单位、最小值和最大值，用于描述允许范围。
- 当前配方逻辑及已发现问题均标记为“未使用、暂不处理”；后续确认启用时必须重新核对最终源码、参数模型、版本规则和权限口径。

## 9. 客户端发布、首装与状态

### 9.1 发布对象与标准发布链路

- 客户端发布对象分为宿主和插件。发布数据按组件、版本和实际产物分层管理。
- 正常发布顺序固定为：先生成真实宿主或插件产物，再通过对应的标准化发布链路执行文件结构、清单、哈希、兼容性和元数据校验，校验成功后才登记为正式发布。
- 生产发布同样必须使用标准化发布链路，不允许通过手工登记元数据、直接填写下载地址或直接修改状态绕过真实产物校验。
- 每次发布都必须填写本次优化内容或变更摘要，不允许使用空白发布说明。
- 发布管理员负责标准发布、归档和版本维护；首装操作员只负责为其授权设备生成首装安装包。

### 9.2 版本保留与发布历史

- 默认只保持三个有效、可向客户端分发的版本。
- 超出默认保留数量的正常历史版本可以停止分发，但其发布详情必须继续保留。
- 正常有效组件的历史详情至少包括版本、状态、发布人、发布时间、发布说明、文件信息、哈希、文件大小、兼容性、依赖关系和产物信息。
- 保留历史详情不等于永久保留所有实际包文件；删除实际发布文件属于高危操作，只能由唯一 Admin 执行。
- 对于误建、名称错误或已经确认废弃的插件，唯一 Admin 可以执行整体永久删除。删除范围同时包括：
  - 发布管理页面中的插件组件条目。
  - 该插件的全部版本、发布历史和产物元数据。
  - 文件存储中的全部实际插件包文件。
- 插件整体删除完成后，管理页面、历史查询和客户端下载目录中均不得继续出现该插件。
- 上述整体删除是错误或废弃插件的明确例外，不适用于正常有效插件；删除操作仍须二次确认并记录结构化操作审计。

### 9.3 动态首装

- 首装由人员在下载时临时选择所需插件，并为每个所选插件动态选择其有权操作的设备，不预先固化为固定的人员、工序或设备组合。
- 人员可以只选择正极模切、只选择负极模切，或同时选择正负极模切；Cloud 根据本次选择动态组装一个首装安装包并提供下载。
- 动态选择能力必须保留，不能改成固定套餐、固定工序映射或后台自动猜测。
- 每次生成安装包都必须保留不可变的生成记录，至少包括所选设备、所选插件、宿主版本、插件版本、渠道、目标运行环境、操作人和生成时间。
- 首装生成记录用于追溯当次实际组装内容，不等于建立不可变的永久设备插件配置。
- 首装完成后的正常版本更新由 Launcher 按正式发布目录自动完成，网页不作为客户端日常更新入口。

### 9.4 版本状态与运行状态

- 设备版本上报和客户端运行心跳是两个独立事实源，不得互相替代。
- 版本上报只用于说明设备当前安装版本以及与正式发布目录之间的差异；运行心跳只用于说明客户端进程运行状态。
- 版本上报必须按上报时间保持单调：旧于当前快照的上报必须拒绝；相同时间且内容相同的上报按幂等成功处理；相同时间但内容不同的上报必须按冲突拒绝。
- 版本状态不得因为收到请求的时间较新而覆盖实际 `ReportedAtUtc` 更晚的快照。
- 运行状态继续按运行心跳独立计算，不能因为版本为最新就显示为正在运行，也不能因为没有版本更新就推断客户端正常。

## 10. 生产数据与过站

### 10.1 事实来源与职责边界

- Cloud 只归档 Edge 上传的真实工序完成事实，不负责判断前一道或下一道工序、生产放行条件、MES 放行或 MES 流转。
- 当前 AI 与人员查询所称的生产记录，来源是 `pass_station_records`；小时产能来自独立的 `hourly_capacity` 统计事实，两者不能混成同一类记录或互相替代。
- 当前正式启用的过站类型只有 `cp / 正极模切` 和 `ap / 负极模切`，其它未投产或已退役类型必须按未知 `typeKey` 拒绝。
- 一次真实工序完成形成一条过站记录。公共记录包括类型、设备、弹夹号、结果、完成时间、接收时间、防重键和扩展字段；CP/AP 的 `barcode` 当前表示弹夹号，不表示电芯条码。
- CP/AP 扩展字段包括 `plcCode`、`plcName`、`clipSlot`、`startTime`、`punchingQuantity` 和 `punchingSpeed`。

### 10.2 上传身份、校验与接收语义

- 上传令牌中的设备身份必须与请求 `DeviceId` 一致；设备当前登记的工序还必须与路由中的 `typeKey` 一致，AP 设备不得上传 CP 数据，CP 设备也不得上传 AP 数据。
- 新上传的 CP/AP 记录必须满足：
  - `clipSlot` 必填，且只能为 `MG1` 或 `MG2`。
  - `cellResult` 只能为 `OK` 或 `NG`。
  - `startTime` 与 `completedTime` 必须使用 UTC，且开始时间不得晚于完成时间。
  - 数值字段必须符合过站 Schema 声明的范围和精度。
- 历史记录的读取保持兼容：历史数据缺少 `clipSlot` 时仍可查询和展示；该兼容不能成为新上传继续缺失 `clipSlot` 的理由。
- 上传接口返回“已接受”只表示请求及对应 Outbox 消息已经可靠登记，不代表后台消费者已经完成最终生产记录落库。

### 10.3 防重与批次冲突

- 单条记录继续使用完整业务内容哈希防重。完全相同的类型、设备、弹夹号、结果、完成时间和扩展字段重试时按幂等成功处理。
- 当前不引入单条客户端事件 ID，不修改 Edge 或插件上传协议；完整内容发生变化时视为另一条内容，不套用“同一事件更新”语义。
- 批次携带 `RequestId` 时，Cloud 必须同时识别批次内容：
  - 相同 `RequestId` 且内容相同，按幂等成功处理。
  - 相同 `RequestId` 但内容不同，必须明确返回冲突，第二批数据不得被静默当成重复而丢弃。

### 10.4 人员查询与错误数据处理

- 普通人员查询过站数据时必须同时具备生产查看功能权限和目标设备范围，只能看到二者交集内的数据。
- 过站页面获取筛选候选项时，只使用满足展示和过滤需要的最小工序、设备信息，不得依赖 Admin 专属设备接口，也不得借候选查询扩大业务数据权限。
- 生产记录默认不可修改、不可删除；普通人员及普通业务管理员均无生产记录写入权限。
- 唯一 Admin 可以直接更正或物理删除确认错误的单条生产记录。操作必须填写原因、二次确认并进入结构化审计：
  - 更正时保存修改前值、修改后值、原因、操作人和时间。
  - 删除时保存删除前完整记录快照、原因、操作人和时间。
- 人员和 AI 查询在 `completedTime` 相同时必须增加稳定的次级排序键，保证翻页、重复查询和审计定位结果稳定。

## 11. AI 只读 API

### 11.1 现有读取能力

| 能力 | 接口 | 权限 |
| --- | --- | --- |
| 设备 | `GET /api/v1/ai/read/devices` | `AiRead.Device` |
| 工序 | `GET /api/v1/ai/read/processes` | `AiRead.Process` |
| 客户端发布 | `GET /api/v1/ai/read/client-releases` | `AiRead.ClientRelease` |
| 设备客户端状态 | `GET /api/v1/ai/read/device-client-states` | `AiRead.DeviceClientState` |
| 产能汇总 | `GET /api/v1/ai/read/capacity/summary` | `AiRead.Capacity` |
| 小时产能 | `GET /api/v1/ai/read/capacity/hourly` | `AiRead.Capacity` |
| 设备日志 | `GET /api/v1/ai/read/device-logs` | `AiRead.DeviceLog` |
| 生产记录 | `GET /api/v1/ai/read/production-records` | `AiRead.ProductionRecord` |
| 人员身份状态 | `GET /api/v1/ai/identity/users/{cloudUserId}/status` | `AiRead.IdentityStatus` |

- AI 业务数据接口只允许 `ai-service-account` 服务身份调用，并同时要求当前接口对应的 `AiRead.*` 权限。
- AI 业务能力保持 GET 只读，不得借 AI 接口创建、修改、删除、补录、审批、派发或触发 Cloud 业务流程；读取审计属于独立的横切记录，不改变业务数据。
- 当前统一限制保留为每个来源 IP 每分钟最多 60 次；单次默认及最大返回 100 行，涉及时间范围的查询最长 30 天，并记录结构化查询审计。
- 生产数据只通过通用 `production-records` 查询，不为 CP、AP 另建专用旁路接口。查询可使用类型、工序、设备、PLC、弹夹号、结果和时间范围等正式过滤条件。
- AI 生产查询只返回公共列和当前过站 Schema 明确声明的字段，不返回原始 `payload_jsonb`，也不返回设备名称、设备编码、上传目标等传输元数据。

### 11.2 委托范围与系统账号

- 普通人员发起的 AI 任务必须携带当前委托用户及其设备范围；缺少委托用户或委托设备声明时必须拒绝，不能自动升级为全局访问。
- 设备、设备客户端状态、产能、设备日志和生产记录等设备范围数据，必须限制在委托声明与该人员当前有效设备授权的交集内。
- 每次委托读取都必须实时复核人员账号状态和当前设备授权；过期令牌中的旧设备声明不能继续产生访问权。
- 工序和客户端发布属于全局主数据或发布目录，但普通 AI 任务仍须先建立有效委托身份，并具备对应 `AiRead.*` 权限。
- 只有经过明确标记和独立授权的系统 AI 账号可以执行全局读取；不能仅凭“缺少委托声明”推断为系统账号。
- 委托 AI 只能查询当前委托用户本人的身份状态；只有明确标记并单独授权的系统身份集成账号可以查询任意用户。

### 11.3 查询契约

- 不支持、拼写错误或不适用于当前接口的查询参数必须返回明确的 `400 Bad Request`，不得静默忽略后继续执行更宽范围查询。
- 必须时间限定的生产查询应要求明确时间范围或正式预设，不能以漏传时间条件换取无界查询。
- 同一完成时间的生产记录必须使用稳定次级键排序；分页条件和响应顺序必须保持一致。
