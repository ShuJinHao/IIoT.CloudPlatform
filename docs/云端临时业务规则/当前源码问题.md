# 云端当前源码问题

## 1. 文档定位

- 本文记录当前源码与本轮已确认业务规则之间的差异，供其它窗口修改完成后统一处理。
- “已确认问题”已经具有明确目标口径；“待确认观察”只记录源码事实和风险，不代表已经批准修改。
- 本轮不根据本文修改源码、接口、数据库、前端或测试。
- 生产过站、AI 查询及相关页面源码当前正在其它窗口并行修改；本节新增结论只代表本轮读取时的源码快照，后续处理前必须重新读取最终源码。

## 2. 已确认问题

### CLOUD-TEMP-001：个人权限接口可写入任意权限，存在直接提权风险

- 严重程度：严重。
- 当前行为：
  - `UpdateUserPermissions` 只要求 `Employee.UpdateAccess`。
  - 调用者可以指定任意目标用户，并提交任意权限字符串。
  - 服务端没有限制为唯一 Admin，也没有用正式权限清单校验字符串。
  - HrAdmin 因为拥有 `Employee.UpdateAccess`，理论上可以给自己或他人增加高危权限。
- 已确认规则：
  - 个人特批权限只能由唯一 Admin 维护。
  - RoleAdmin 只能维护非 Admin 角色及白名单内权限。
  - HrAdmin 只能分配已有角色和设备范围，不能维护任何权限内容。
- 后续验收重点：
  - 非 Admin 调用个人权限维护必须被拒绝。
  - 未定义权限字符串必须被拒绝。
  - 目标为 Admin 时，普通人员权限接口不得产生任何修改。
- 主要源码：`src/services/IIoT.IdentityService/Commands/Human/UpdateUserPermissions.cs`、`src/infrastructure/IIoT.EntityFrameworkCore/Identity/RolePolicyService.cs`。

### CLOUD-TEMP-002：Admin 账号缺少统一保护，人员权限边界可以被绕过

- 严重程度：严重。
- 当前行为：
  - `UpdateEmployeeProfile` 可以修改启停状态，只持有 `Employee.Update` 就可能停用人员，从而绕过独立的 `Employee.Deactivate` 权限。
  - 资料修改在不提交角色时缺少 Admin 目标保护，非 Admin 可能修改或停用 Admin 对应人员和账号。
  - `ResetPassword` 只要求 `Employee.Update`，HrAdmin 可看到人员 ID，因此可能重置 Admin 密码。
  - 角色定义和角色权限维护对 Admin 角色的保护不一致。
- 已确认规则：
  - 系统只有一个正式 Admin。
  - 非 Admin 不得修改、停用、终止、重置 Admin 密码或变更 Admin 角色。
  - Admin 只能修改自己的密码，不能通过“重置他人密码”入口重置 Admin 密码。
  - HrAdmin 可停用和重新启用普通人员，永久终止仅限唯一 Admin。
  - 唯一 Admin 可以重置普通账号密码。
- 后续验收重点：
  - 所有人员管理写入口使用统一的 Admin 目标保护。
  - 基础资料修改不能绕过停用、角色、密码或权限的独立授权。
  - 永久终止普通人员只能由唯一 Admin 执行。
- 主要源码：`src/services/IIoT.EmployeeService/Commands/Human/Employees/UpdateEmployeeProfile.cs`、`DeactivateEmployee.cs`、`TerminateEmployee.cs`、`src/services/IIoT.IdentityService/Commands/Human/ResetPassword.cs`。

### CLOUD-TEMP-003：HrAdmin 无法完成设备范围授权

- 严重程度：高。
- 当前行为：
  - HrAdmin 具有 `Employee.UpdateAccess`，人员页面也提供设备范围维护。
  - 页面加载候选设备时调用 `/human/devices/all`。
  - 后端查询除要求 `Device.Read` 外，还显式限定 Admin。
  - HrAdmin 内置权限不包含 `Device.Read`，即使补上该权限也仍会被 Admin 限制拒绝。
- 已确认规则：
  - HrAdmin 可以维护普通人员的设备范围。
  - 应提供只服务于人员授权的最小候选设备列表。
  - 获取候选列表不能顺带赋予 HrAdmin 全部设备业务数据读取权限。
- 后续验收重点：
  - HrAdmin 能加载正式设备候选项并完成授权保存。
  - HrAdmin 仍不能借候选查询读取设备敏感详情或其它未授权业务数据。
- 主要源码：`src/services/IIoT.ProductionService/Queries/Human/Devices/GetAllDevices.cs`、`src/ui/iiot-web/src/features/employees/useEmployees.ts`。

### CLOUD-TEMP-004：DeviceAdmin 模板与设备高危操作边界自相矛盾

- 严重程度：高。
- 当前行为：
  - DeviceAdmin 模板包含 `Device.Create`、`Device.Delete` 和 `Device.CascadeDelete`。
  - 注册设备接口又显式要求 Admin，所以 `Device.Create` 对非 Admin DeviceAdmin 实际无效。
  - 删除设备接口没有 AdminOnly 限制，具备双删除权限且被分配目标设备的 DeviceAdmin 可以删除设备。
  - 当前正式规则要求设备注册和设备级联删除均为管理员专属。
- 已确认规则：
  - 新设备注册和设备级联硬删除都只能由唯一 Admin 操作。
  - DeviceAdmin 只能查看和维护已授权设备，不得注册或删除设备。
- 后续验收重点：
  - 角色模板、后端授权、页面按钮和正式规则保持同一口径。
  - 设备删除继续保留双权限点、影响预览、二次确认和结构化审计。
- 主要源码：`src/services/IIoT.Services.Contracts/Contracts/Authorization/SystemRolePermissionTemplates.cs`、`src/services/IIoT.ProductionService/Commands/Human/Devices/RegisterDevice.cs`、`DeleteDevice.cs`。

### CLOUD-TEMP-005：人员停用后已有会话不会立即失效

- 严重程度：严重。
- 当前行为：
  - 停用人员时会撤销 Refresh Token。
  - 已签发的 Access Token 不会被主动失效。
  - 授权阶段会重新读取权限和设备范围，但不会统一重新检查账号及人员启用状态。
  - Admin 绕过取决于当前 Token 中的角色，在 Token 有效期内风险更高。
- 已确认规则：
  - 停用和永久终止必须立即使访问令牌、刷新令牌和登录会话全部失效。
  - 重新启用后必须重新登录，停用前会话不得恢复。
- 后续验收重点：
  - 停用成功后的下一次请求立即返回未认证或无权访问。
  - Access Token、Refresh Token 和 OIDC 登录会话均覆盖。
  - 普通用户和 Admin 身份链都不能绕过状态检查。
- 主要源码：`src/services/IIoT.EmployeeService/Commands/Human/Employees/DeactivateEmployee.cs`、`src/services/IIoT.Services.CrossCutting/Requests/Behaviors/AuthorizationBehavior.cs`、身份令牌签发与刷新链路。

## 3. 待确认观察

### CLOUD-TEMP-OBS-001：接口校验长度与数据库字段长度不一致

- EmployeeNo、RealName 的接口上限为 64，数据库上限为 50。
- DeviceName 的接口上限为 128，数据库上限为 100。
- 风险是请求先通过业务校验，最后以数据库异常失败，错误语义不稳定。

### CLOUD-TEMP-OBS-002：Device 到 Process 缺少数据库外键约束

- 注册设备时应用层会检查工序存在，删除工序时也会查询设备引用。
- 数据库模型未建立 Device 到 MfgProcess 的正式外键，完整性主要依赖应用层路径。
- 需要确认是否补数据库外键，以及存量数据迁移和删除约束。

### CLOUD-TEMP-OBS-003：工序编码唯一规则和输入校验未闭合

- 当前工序编码唯一比较区分大小写，可能同时存在 `AP` 和 `ap`。
- 工序创建、更新缺少与数据库长度一致的业务校验。
- 需要确认编码是否统一规范化，以及历史编码迁移规则。

### CLOUD-TEMP-OBS-004：设备注册与 BootstrapSecret 生成不在同一时点

- 注册设备只生成 DeviceId 和 ClientCode，不生成 BootstrapSecret。
- BootstrapSecret 在生成安装包绑定时才创建或轮换。
- 因此新注册设备在生成安装绑定前不能完成 bootstrap。
- 需要确认这是否是预期的“两阶段注册”，以及重复生成安装包时旧绑定的失效口径。

### CLOUD-TEMP-OBS-005：内置角色模板是追加式最低权限，不是精确模板

- 播种逻辑只补回模板中缺少的权限，不会移除角色上的额外权限。
- 人工删除内置模板权限后，后续播种可能再次补回。
- 需要明确内置角色是不可削减的最低权限模板，还是应保持精确权限集合。

### CLOUD-TEMP-OBS-006：设备删除影响展示与实际删除范围可能不一致

- 后端实际删除范围包含 PLC runtime state 等关联状态。
- 前端影响 DTO 和列表未完整覆盖全部删除项，文字确认也没有形成稳定强制约束。
- 正式规则已经要求影响范围、确认内容和审计摘要覆盖所有实际删除数据，后续应结合当前并行修改结果重新核对。

## 4. 配方源码问题：未使用、暂不处理

- 配方当前没有投入实际使用。本节只备案当前源码风险，不安排本轮修复，也不据此提前确定未来配方的最终业务设计。

### CLOUD-TEMP-RECIPE-001：参数结构只有范围描述，缺少明确的目标值语义

- 当前标准参数结构只有参数标识、名称、单位、最小值和最大值，没有明确的设定值、目标值或其它实际执行值。
- 后端虽然可能接收额外 JSON 字段，但当前页面的解析和升级流程只保留标准范围字段，额外字段可能丢失。
- 后续启用配方前，需要重新定义实际执行参数、范围参数和版本升级时的字段保留规则。

### CLOUD-TEMP-RECIPE-002：版本升级不保证版本单调递增

- 当前升级入口只校验版本字符串格式，没有保证新版本高于现有版本。
- 已归档版本仍可作为升级来源，因此可能创建相同版本、较低版本或语义倒退的版本。
- 后续启用时需要统一版本格式、比较规则、升级来源和冲突处理。

### CLOUD-TEMP-RECIPE-003：删除旧版本后可重新创建多个活动版本

- 当前归档版本可以被硬删除。
- 重名检查主要依赖同名 `V1.0` 是否存在；删除旧 `V1.0` 后，可以再次创建同名活动 `V1.0`，而原有更高活动版本仍可能存在。
- Edge 查询会取得所有 `Active` 配方，因此同一配方可能同时存在多个活动版本。

### CLOUD-TEMP-RECIPE-004：数据库缺少关键唯一性和活动版本约束

- 当前数据库没有对工序、设备、配方名称和版本建立完整唯一约束。
- 数据库也没有保证同一工序、设备和配方名称只能存在一个 `Active` 版本。
- 并发创建、升级或应用层路径绕过时，完整性主要依赖应用代码和分布式锁。

### CLOUD-TEMP-RECIPE-005：前后端权限和可操作状态不一致

- 配方创建页面获取候选设备时复用了 Admin 限定的设备查询，非 Admin 配方管理人员可能具有配方权限却无法取得候选设备。
- 页面删除入口使用的权限与后端 `Recipe.Delete` 要求不一致，页面展示的可删除状态也与后端只允许删除归档版本的规则不一致。
- 后续启用配方时，需要统一角色模板、候选查询、页面按钮、后端权限和版本状态约束。

## 5. 客户端发布与状态：后续重点处理

### CLOUD-TEMP-CLIENT-001：旧手工登记接口可以绕过标准发布链路

- 严重程度：严重。
- 当前仍存在宿主和插件的旧手工登记接口，只要求发布管理权限即可直接提交 URL、哈希、文件大小、签名、发布人和状态等元数据。
- 接口可以写入包括 `Published`、`Deleted` 在内的状态，并可覆盖既有版本元数据或产物记录。
- 该路径没有执行标准宿主或插件发布链路中的真实文件、包结构、清单、哈希、锁、审计和失败恢复校验。
- 已确认规则是“先生成真实产物，再标准化发布”；旧手工登记路径不得继续作为正式发布旁路。

### CLOUD-TEMP-CLIENT-002：通用状态接口允许任意状态跳转和版本复活

- 严重程度：严重。
- 当前通用状态更新接口只要能够解析状态枚举，就可以直接写入目标状态。
- 接口没有统一状态转换图，也没有完整执行文件存在性、使用中保护、并发锁、结构化审计和恢复校验。
- 因此可以直接标记 `Published`、`Deleted`、`DeleteFailed`、`DeleteRequested`，也可能把已经结束的版本重新改回可用状态。
- 发布、归档、文件删除和失败恢复必须各自通过标准业务动作完成，不能继续由通用状态写入口替代。

### CLOUD-TEMP-CLIENT-003：动态首装选择结果没有形成完整生成记录

- 严重程度：高。
- 当前页面支持人员动态勾选插件并为插件选择设备，后端也会按本次选择组装安装包。
- 生成完成后主要持久化设备的新 BootstrapSecret 哈希；现有审计没有完整记录所选设备、插件、宿主版本、插件版本、渠道和目标运行环境。
- 因此动态选择功能虽然存在，但当次实际组装内容无法形成完整、不可变、可查询的生成记录。
- 后续治理必须保留动态选择方式，同时补齐每次生成结果的追溯；不得借此改成固定设备插件映射。

### CLOUD-TEMP-CLIENT-004：延迟到达的旧版本上报可以覆盖新快照

- 严重程度：高。
- 当前版本上报会直接替换设备客户端版本快照，没有按 `ReportedAtUtc` 执行单调、幂等和同时间冲突判断。
- 延迟到达的旧上报可以覆盖更新快照，并因为服务端接收时间较新而被误认为新鲜状态。
- 应与运行心跳采用一致的时间顺序原则：拒绝旧上报、接受同内容幂等、拒绝同时间不同内容。

### CLOUD-TEMP-CLIENT-005：插件版本缺少统一 SemVer 校验和排序

- 严重程度：高。
- 独立插件发布没有统一强制 SemVer。
- 当前比较逻辑在无法按系统版本解析时会退回字符串排序，预发布版本或任意版本字符串可能产生错误顺序。
- 该问题会同时影响首装选择最高版本、默认三个版本保留、更新状态和最新版本判断。

### CLOUD-TEMP-CLIENT-006：删除文件按钮的前端权限与 Admin 专属规则不一致

- 严重程度：高。
- 当前发布管理页面按普通发布管理权限展示“删文件”操作。
- 后端文件硬删除实际要求 Admin 身份和专用硬删除权限，因此非 Admin 发布管理员会看到按钮但调用后得到拒绝。
- 已确认只有唯一 Admin 可以删除宿主或插件实际发布文件；页面可见性、接口授权和角色模板必须保持一致。

### CLOUD-TEMP-CLIENT-007：历史查询没有返回完整发布详情

- 严重程度：高。
- 当前历史接口主要返回版本、状态、创建时间、发布时间、删除时间、原因和失败信息。
- 数据库版本记录中已有的发布说明、哈希、文件大小、发布人、签名、兼容性、依赖和产物详情没有完整提供给历史查询。
- 正常有效组件必须保留并能查询全部历史发布详情，不能只保留版本号和状态摘要。
- 对误建或废弃插件执行 Admin 整体删除是已确认例外；该能力本身不登记为缺陷。

### CLOUD-TEMP-CLIENT-008：默认三个可分发版本的保留规则没有闭合

- 严重程度：高。
- 当前保留策略默认数量为三个，但超出数量且仍被设备使用的 `Published` 版本会改为 `Deprecated`。
- `Deprecated` 版本仍会出现在 Edge/Public 可分发目录中，因此实际可下载版本可能超过三个。
- 正常历史详情需要永久保留，但默认可分发目录只能保持三个版本；历史元数据保留与包文件、客户端下载可见性必须分开处理。

### CLOUD-TEMP-CLIENT-009：插件整体删除需要按已确认范围重新核对

- 严重程度：高。
- 唯一 Admin 删除误建、名称错误或已废弃插件属于已确认业务能力，不是禁止项。
- 后续需要核对整体删除是否同时覆盖发布管理页面中的组件条目、全部版本与发布历史元数据、全部实际插件包文件，并从客户端下载目录中消失。
- 普通发布管理员不得执行整体删除；正常有效插件不得套用该例外。
- 整体删除应保留最小结构化操作审计，但不要求继续保留被删除插件的发布历史。

## 6. 生产数据与过站：后续重点处理

### CLOUD-TEMP-PRODUCTION-001：上传类型未与设备登记工序绑定

- 严重程度：严重。
- 当前上传链路会校验设备存在、令牌设备身份与请求 `DeviceId` 一致，但没有继续校验设备登记的 `ProcessId` 是否对应路由 `typeKey`。
- 因此 AP 设备可能向 `cp` 路由上传数据，CP 设备也可能向 `ap` 路由上传数据，Cloud 仍会接受并归档。
- 已确认上传类型必须与设备当前登记工序一致，不匹配时应在登记 Outbox 前明确拒绝。

### CLOUD-TEMP-PRODUCTION-002：批次 RequestId 冲突会被当成重复成功

- 严重程度：严重。
- 当前携带 `RequestId` 的批次只使用 `request:{RequestId}` 作为批次防重键，没有保存和比较批次内容指纹。
- 相同 `RequestId`、相同内容重试能够正确按幂等成功处理；但相同 `RequestId`、不同内容也会返回重复成功，第二批内容不会进入 Outbox，形成静默数据丢失。
- 后续只治理批次冲突：相同 ID、相同内容幂等成功；相同 ID、不同内容明确返回冲突。
- 单条完整内容哈希是当前认可的精确内容防重方案，不登记为缺陷；本轮不引入客户端事件 ID，也不修改 Edge 或插件协议。

### CLOUD-TEMP-PRODUCTION-003：ProductionViewer 具备查看权限仍可能看到空页面

- 严重程度：高。
- 过站页面路由主要要求 `Device.Read`，但页面加载筛选数据时还调用需要 `Process.Read` 的工序查询和 Admin 专属的 `/human/devices/all`。
- `ProductionViewer` 等普通查看角色即使具有生产查看权限和设备范围，也可能因候选接口被拒绝而得到空工序、空设备列表，最终页面无法正常查询。
- 后续应提供满足过站筛选需要的最小候选数据，并继续按功能权限与设备范围交集限制生产记录。

### CLOUD-TEMP-PRODUCTION-004：CP/AP 新上传字段校验没有闭合

- 严重程度：高。
- 当前 `cellResult` 主要校验非空和长度，没有强制为 `OK`、`NG`。
- `clipSlot` 为兼容历史记录被配置成可选，导致新上传也可以继续缺失；`startTime` 主要验证可解析，没有完整强制 UTC 及开始时间不晚于完成时间。
- Schema 声明的数值精度也没有形成完整的新上传约束。
- 后续必须区分“历史读取兼容”和“新数据写入校验”：历史缺少弹夹位仍可读，新上传必须满足已确认的枚举、UTC、时间顺序、范围和精度规则。

### CLOUD-TEMP-PRODUCTION-005：Human 查询返回了未声明的传输元数据

- 严重程度：高。
- 当前 Human 过站查询会把 `payload_jsonb` 中的全部键转换为返回字段，没有只投影当前 `typeKey` Schema 声明的业务字段。
- 随上传进入载荷的 `deviceName`、`deviceCode`、`uploadTargets` 等传输元数据可能因此出现在人员查询结果中。
- Human 与 AI 均应只返回公共列和 Schema 声明字段，不返回原始载荷或未声明传输元数据。

### CLOUD-TEMP-PRODUCTION-006：缺少 Admin 单条记录更正和物理删除审计链路

- 严重程度：高。
- 当前没有满足已确认口径的生产记录单条更正、物理删除、原因填写、二次确认和修改前后审计链路。
- 已确认正常记录默认不可修改、不可删除，普通人员及普通业务管理员无写入口。
- 唯一 Admin 对确认错误的记录可以直接更正或物理删除，但必须保存修改前后值或删除前完整快照及结构化操作审计。

### CLOUD-TEMP-PRODUCTION-007：Human 详情查询存在记录存在性泄露

- 严重程度：中。
- 当前详情链路先按记录 ID 查询数据，再判断记录设备是否位于当前人员范围内。
- 未授权调用者可能从“记录不存在”和“记录存在但无权访问”的差异中判断某个记录 ID 是否真实存在。
- 后续查询应把设备范围前置到数据检索条件，或对越权与不存在返回不可区分的外部语义。

### CLOUD-TEMP-PRODUCTION-008：生产记录分页排序缺少稳定次级键

- 严重程度：中。
- 当前 Human 与 AI 生产记录查询主要只按 `completed_time DESC` 排序。
- 多条记录完成时间相同时，数据库没有稳定的次级顺序，翻页或重复查询可能出现记录重复、遗漏或顺序变化。
- 后续必须增加稳定且唯一的次级排序键，并让分页条件与响应排序使用同一顺序。

## 7. AI 只读 API：后续重点处理

### CLOUD-TEMP-AI-001：缺少委托声明时会隐式获得全局范围

- 严重程度：严重。
- 当前 AI Scope 解析在没有委托用户和设备声明时直接返回 `Global`，无法区分“普通任务漏传委托信息”和“明确授权的系统 AI 账号”。
- 普通 AI 调用如果声明遗漏或上游组装错误，可能因此获得全局数据范围。
- 后续必须使用明确系统账号标记判断全局访问；普通任务缺少委托声明时直接拒绝。

### CLOUD-TEMP-AI-002：委托范围没有实时复核人员状态和设备授权

- 严重程度：严重。
- 当前 Cloud 主要信任 AI 令牌中的委托用户和设备声明，没有在每次读取时重新检查人员是否仍启用、账号是否有效以及设备是否仍归属该人员。
- 人员被停用或设备授权被移除后，旧令牌声明在有效期内仍可能继续读取旧范围数据。
- 后续委托读取必须把声明范围与人员当前有效状态、当前设备授权实时求交；失效人员应整体拒绝。

### CLOUD-TEMP-AI-003：身份状态接口允许查询任意用户

- 严重程度：高。
- 当前调用者具备 `AiRead.IdentityStatus` 后，可以在路由中指定任意 `cloudUserId`，没有限制为当前委托用户。
- 已确认普通委托 AI 只能查询委托用户本人的身份状态；只有明确标记并独立授权的系统身份集成账号可以查询任意用户。
- 后续授权必须同时校验账号类型、委托用户与目标用户，不能只校验功能权限字符串。

### CLOUD-TEMP-AI-004：未知查询参数会被静默忽略

- 严重程度：高。
- 当前多数 AI 读取接口只解析认识的查询参数，对拼写错误或不支持的参数不会统一拒绝。
- 调用方原本希望使用的限制条件可能没有生效，接口却继续执行更宽范围查询，结果容易被误认为已按条件过滤。
- 后续所有 AI 读取接口应校验查询参数白名单；未知、不适用或格式错误的参数统一返回明确的 `400 Bad Request`。

## 8. 后续统一处理原则

- 等其它窗口的代码修改完成后，先重新读取最终源码，不按本文假定旧问题仍然存在。
- 对每个已确认问题逐项比较“已修复、部分修复、仍存在、出现新冲突”，不得整批直接套用旧结论。
- 实施时同步调整后端授权、角色模板、前端可见性和受影响测试，避免只修页面或只修接口。
- 完成治理后，将长期有效规则合并到 `../云端规则.md` 或唯一正式专题契约，并删除本临时目录。
