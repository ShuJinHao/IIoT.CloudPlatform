本文是 Cloud 唯一活动短路线图，只保留尚未完成的问题。长期口径以[云端规则](./云端规则.md)和[过站工序扩展规则](./过站工序扩展规则.md)为准；已关闭问题和实施过程只从 Git、PR 与不可变验证证据追溯。

## 生产重试与提交未知

### CLOUD-TEMP-TX-001：正式宿主尚不能安全全局启用 PostgreSQL retry

- 目标规则：[架构和代码](./云端规则.md#6-架构和代码)。
- 当前缺口：HttpApi、DataWorker 与 MigrationWorkApp 的受版本控制默认值仍为 `EnableRetry=false`，生产 compose 只通过 fallback 覆盖 HttpApi、DataWorker，未覆盖 MigrationWorkApp。员工、业务聚合、Edge 上报、客户端发布、共享持久化及 migration/seed 写链均已具备提交前 transient 重放、提交确认丢失和并发漂移闭环；当前只剩动态发现总闭环、真实 PostgreSQL 最终验收和三个宿主 retry 开关。
- 后续批次：`CLOUD-TX-03C` 做动态发现闭环、PostgreSQL 最终验收和三个宿主 retry 开关收口。
- 验收条件：以届时源码动态发现的全部写调用为准，逐项证明已有精确恢复、稳定键/CAS、新增专用提交观察器或调用点已删除；真实 PostgreSQL 故障注入覆盖提交确认丢失、并发漂移和未知结果后，三个宿主才可一致启用 retry 并对生产配置 fail-closed。

## 待确认观察

以下事项只记录待确认风险，不授权直接修改业务语义。

### CLOUD-TEMP-OBS-001：接口与数据库字段长度不一致

- 目标规则：[架构和代码](./云端规则.md#6-架构和代码)。
- 当前缺口：EmployeeNo/RealName 与 DeviceName 的接口上限大于数据库字段上限，合法请求可能最终变成数据库异常。
- 后续批次：`CLOUD-OBS-01`。
- 验收条件：确认统一上限后，接口、领域、数据库和错误语义一致，并覆盖边界值迁移与测试。

### CLOUD-TEMP-OBS-002：Device 到 Process 缺少数据库外键

- 目标规则：[设备和身份链](./云端规则.md#3-设备和身份链)。
- 当前缺口：设备所属工序完整性主要依赖应用检查，数据库未建立正式外键。
- 后续批次：`CLOUD-OBS-01`。
- 验收条件：确认外键及删除策略，存量数据预检通过，应用与数据库使用同一完整性语义。

### CLOUD-TEMP-OBS-003：工序编码唯一与输入规则未闭合

- 目标规则：[过站工序扩展](./云端规则.md#5-过站工序扩展)。
- 当前缺口：工序编码唯一比较区分大小写，输入长度和规范化规则未与数据库闭合。
- 后续批次：`CLOUD-OBS-01`。
- 验收条件：确认大小写、规范化和迁移规则后，创建、更新及数据库唯一约束一致。

### CLOUD-TEMP-OBS-004：设备注册与 BootstrapSecret 生成采用两阶段

- 目标规则：[设备和身份链](./云端规则.md#3-设备和身份链)。
- 当前缺口：设备注册只产生 DeviceId/ClientCode，BootstrapSecret 到安装包生成时才创建或轮换，最终时点和重复生成失效口径尚未确认。
- 后续批次：`CLOUD-OBS-01`。
- 验收条件：明确两阶段契约、轮换与旧绑定失效规则，并覆盖注册、首装和重复生成。

### CLOUD-TEMP-OBS-005：内置角色模板是追加式最低权限

- 目标规则：[人员和权限](./云端规则.md#2-人员和权限)。
- 当前缺口：播种会补回模板缺项但通常保留额外权限，尚未确认各内置角色应采用最低权限还是精确集合语义。
- 后续批次：`CLOUD-OBS-01`。
- 验收条件：逐个内置角色确认模板语义，升级只执行明确允许的增删且不覆盖现场自定义角色。

### CLOUD-TEMP-OBS-007：工序主数据写操作是否统一限定 Admin

- 目标规则：[过站工序扩展](./云端规则.md#5-过站工序扩展)。
- 当前缺口：正式生产启用要求管理员显式创建工序，但工序主数据的创建、修改和删除是否全部限定真实人类 Admin 尚未形成最终业务决策。
- 后续批次：`CLOUD-OBS-01`，先确认业务口径再授权实现。
- 验收条件：逐项确认创建、修改、删除的调用者、权限、在用保护和审计规则；决策前不改变现有接口语义。

### CLOUD-TEMP-OBS-008：Admin 个人特批是否允许扩散治理权限

- 目标规则：[人员和权限](./云端规则.md#2-人员和权限)。
- 当前缺口：个人特批由 Admin 专属维护，但尚未明确该入口是否也必须禁止向普通人员授予角色定义、角色权限维护等治理权限。
- 后续批次：`CLOUD-OBS-01`，先确认白名单或禁止集合。
- 验收条件：确认个人特批的治理权限边界后，权限目录、服务端校验、页面候选、存量预检和结构化审计使用同一口径。

### CLOUD-TEMP-OBS-009：唯一 Admin 是否需要数据库级防线

- 目标规则：[人员和权限](./云端规则.md#2-人员和权限)。
- 当前缺口：恰好一个 Admin 目前由应用入口、migration/seed 预检、事务 advisory lock 和提交前断言保证，数据库没有表达跨 Identity 角色分配与 Employee 完整性的唯一约束。
- 后续批次：`CLOUD-OBS-01`，评审存量、并发、恢复和 PostgreSQL 可实现方案。
- 验收条件：明确是否增加数据库级防线；若增加，迁移必须先报告冲突并 fail-fast，不自动删除、降级或合并账号，且与应用播种矩阵一致。

### CLOUD-TEMP-OBS-010：事务与 Admin 授予静态门禁存在已知覆盖边界

- 目标规则：[测试执行与 CI 对账](./云端规则.md#61-测试执行与-ci-对账)。
- 当前缺口：手工事务执行策略和 Admin 角色授予目前主要由 ArchitectureTests 的 Roslyn/源码静态扫描约束；对新的间接封装、反射、非 C# 写入或其它未建模路径是否需要编译期 Analyzer 或数据库防线尚未确认。
- 后续批次：`CLOUD-OBS-01`，先建立绕过矩阵再决定是否加强。
- 验收条件：列出生产写入面的正反例和当前门禁可见性，确认接受的防线层级；任何加强不得通过宽泛字符串扫描误报或绕开现有受影响测试选择器。
