# 过站工序扩展规则

> **状态：候选实现继续保留，复审问题尚未全部收口；真实 Windows 验收、生产绑定迁移和部署仍未执行，不作为生产部署基线。**

本文档约束 `IIoT.CloudPlatform` 的生产业务记录扩展方式。当前 Cloud 使用“公共检索列 + `payload_jsonb` 扩展字段 + 插件版本能力清单 + Cloud 兼容注册”的模型。`ProcessType` 只表示工序分类；`TypeKey` 只表示插件声明的一种业务记录类别，二者不得画等号。

跨 Cloud 与 EdgeClient 的完整接入清单见 `../../docs/新工序接入手册.md`。

当前 AP、CP 设备插件只启用共同确认的 `die-cutting-completion / 模切完成记录`。历史 `ap`、`cp` 仅作为对应已发布插件能力清单中的 `legacyTypeKeys` 兼容旧数据；它们不是正负极工序、`ModuleId` 或设备身份。报警、能耗、注塑、叠片、匀浆等未确认业务类别不得因示例或旧配置自动启用。

## 固定规则

- Cloud 只归档 Edge 上传的真实工序完成事实，不判断前后工序、生产放行或 MES 流转；`pass_station_records` 与独立的 `hourly_capacity` 是两类事实，不得互相替代。一次真实工序完成形成一条过站记录，CP/AP 的 `barcode` 表示弹夹号而不是电芯条码。
- 新增业务记录类别时，必须先在独立设备插件的版本化 `data-capabilities.json` 声明真实能力，再同步 Cloud 兼容注册、发布签名和查询测试；只改 `pass-station-types.json` 不能赋予插件新能力。
- 不再为每个工序新增独立 DTO、Event、Mapper、SQL、Consumer、Vue 页面或 RabbitMQ endpoint。
- 统一上传接口为 `POST /api/v1/edge/pass-stations/{typeKey}/batch`。`schemaVersion=1`、`schemaVersion=2` 只用于兼容旧记录与旧客户端；具备 `ClientCode + CompletionId + TypeKey` 完整身份、并由实际安装插件版本声明能力的新记录使用严格 `schemaVersion=3`。Cloud 在兼容退出完成前继续读取 v1/v2，但不得把缺少 v3 身份的旧记录伪装成 v3。
- 统一查询接口为 `GET /api/v1/human/pass-stations/{typeKey}`、`GET /api/v1/human/pass-stations/{typeKey}/{id}` 和同筛选条件的 `GET /api/v1/human/pass-stations/{typeKey}/export`。CSV 最多导出 10,000 条，超过上限必须明确失败。
- AI 高频生产数据统一查询接口为 `GET /api/v1/ai/read/production-records`。只有设备绑定插件的实际安装版本声明并通过 Cloud 校验的 `TypeKey` 才能查询；不再为 AI 按工序新增独立查询接口。
- 前端过站页面必须从云端 `GET /api/v1/human/pass-stations/types` 读取 schema 动态渲染。
- 工序扩展字段必须进入 `payload_jsonb`，公共检索锚点保留为普通列。
- 标准 `CellDataBase` 传输元数据可以随批次进入统一链路；业务扩展字段仍必须由当前 `typeKey` schema 明确声明。未知业务字段严格拒绝，Human 列表、详情、CSV 导出与 AI 只投影同一公共字段白名单及 schema 字段，不返回 raw `payload_jsonb` 或传输元数据。
- 上传 token 的设备身份必须与请求 `DeviceId`/`ClientCode` 指向同一设备插件。请求 `processType` 必须与设备当前登记工序一致；路由 `typeKey` 必须由该设备绑定插件的实际安装版本能力清单声明。`ProcessType`、`TypeKey`、`ModuleId` 不要求相等，任一身份、工序或能力不匹配都必须在 Outbox 登记前拒绝。
- 携带 `RequestId` 的批次必须同时识别规范化批次内容：相同 ID 且内容相同按幂等成功，相同 ID 但内容不同固定返回 `409 cloud_write_conflict`；历史登记只允许从保留的 Outbox 回填内容指纹，无法还原必须失败并列出记录，不得猜测；单条记录继续使用完整业务内容哈希防重。
- 上传接口返回“已接受”只表示请求及对应 Outbox 消息已经可靠登记，不代表后台消费者已经完成最终 `pass_station_records` 落库。请求接收、Outbox 登记、消费者处理、最终持久化和查询可见必须分别取证，不得用任一前置成功替代最终落库。
- 过站页面筛选候选只使用当前人员授权范围内的设备接口，并由设备派生工序；不得依赖 Admin 专属全量接口，也不得借候选查询扩大业务数据权限。设备、schema、列表或导出加载失败必须明确显示，不得吞错为空列表。
- Human 列表、详情和导出必须同时满足生产查看权限和设备范围，并在数据库检索条件中应用设备范围；详情越权与不存在统一返回 NotFound。排序固定为完成时间倒序、记录 ID 倒序。
- 生产记录默认不可修改、不可删除；只有真实人类 Admin 可以更正或物理删除确认错误的单条记录，并必须填写原因、二次确认、保存前后值或删除前完整快照及结构化审计。

## 公共列

`pass_station_records` 固定保留以下普通列：

- `id`
- `type_key`
- `device_id`
- `barcode`
- `cell_result`
- `completed_time`
- `received_at`
- `deduplication_key`
- `payload_jsonb`

只有这些字段可以直接参与通用高频过滤和排序。新增工序字段如果需要高频过滤、排序或统计，必须单独评估是否提升为普通列，或新增 JSONB 表达式索引。

当前 AP/CP 模切完成记录将弹夹号映射到 `barcode`，并声明 `plcCode`、`plcName`、`clipSlot`、`startTime`、`punchingQuantity`、`punchingSpeed`。v3 新上传的 `ClientCode` 必须与设备令牌和 Cloud 设备一致，`processType` 必须与设备登记工序一致，路由及事实中的 `typeKey` 必须命中实际插件版本声明的 `die-cutting-completion`，每条事实还必须具有稳定且批内不重复的 `CompletionId`；`plcCode`、真实 `plcName` 和全部 Schema 字段必须满足必填约束，`clipSlot` 只允许 `MG1`、`MG2`，`cellResult` 只允许 `OK`、`NG`；`startTime` 与 `completedTime` 必须为 UTC 且开始不晚于完成，数值字段必须满足 Schema 范围与精度。历史 v1/v2 或历史记录缺少字段时仍可读取和展示，但该兼容不得放宽 v3 新写入。单台 PLC 高频查询由 `(type_key, payload_jsonb->>'plcCode'/'plcName', completed_time)` 表达式索引覆盖。

## 配置项

每个 Cloud 兼容业务记录类别必须包含：

- `typeKey`：插件业务记录类别键；在对应插件版本内唯一，并与签名 `data-capabilities.json` 一致，不得要求等于工序编码或 `ModuleId`。
- `legacyTypeKeys`：可选，只列已有历史数据的兼容键；不得作为新记录默认写入值或永久业务映射。
- `displayName`：中文显示名。
- `description`：前端页面说明。
- `supportedModes`：支持的查询模式。
- `fields`：工序扩展字段定义。
- `listColumns`：列表展示列。
- `detailSections`：详情页分组展示字段。

字段支持类型：

- `string`
- `number`
- `integer`
- `boolean`
- `datetime`
- `enum`

字段支持规则：

- `required`
- `maxLength`
- `min`
- `max`
- `unit`
- `precision`
- `options`

云端启动时会校验配置。`typeKey` 重复、字段 key 重复、字段 key 不安全、列表或详情引用不存在字段，都会导致服务启动失败。

## 新增业务记录类别步骤

以中性占位类别 `<typeKey>` 为例：

1. 先取得业务确认，并在该独立设备插件的 `data-capabilities.json` 增加版本化能力项。
2. 设置安全且在该插件版本内唯一的 `typeKey`，定义作用范围、查询模式、字段和公开字段。
3. 发布插件包，使能力文件、逐文件清单、包摘要和发布签名形成不可变证据。
4. 在 `src/hosts/IIoT.HttpApi/config/pass-station-types.json` 同步 Cloud 兼容注册；只有确有旧数据时才增加 `legacyTypeKeys`。
5. 在 `fields`、`listColumns` 和 `detailSections` 中配置 Cloud 列表和详情投影。
6. 验证设备绑定插件的实际安装版本能力匹配、上传拒绝未声明类别、Human/AiRead 动态 Schema 及页面渲染。

除非新增公共检索字段、全新业务链路或新的持久化策略，否则不得新增 per-process 代码文件；插件自身的独立业务实现和独立业务文档不受此句限制。

生产启用必须由管理员显式创建工序主数据和对应中文客户端设备；部署、migration 与 seed 不得自动创建设备、注册 ClientCode 或轮换 bootstrap secret。正式退役工序必须同时清除活动 schema、示例和入口；必要历史发布审计只归档并从 catalog 隐藏。

## 允许新增代码的例外

只有以下情况可以突破“只改配置”的规则：

- 新字段需要成为系统级公共检索锚点。
- 需要按 JSON 内字段做高频过滤、排序或聚合统计。
- 需要全新的业务链路，不再属于普通过站追溯。
- 需要独立权限、审计或状态流转规则。

出现这些情况时，必须先说明影响范围，再单独开小 PR，不得混入普通工序扩展。
