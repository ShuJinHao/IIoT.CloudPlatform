## 1. Cloud 定位与两类业务视图

Cloud 是人员、账号、权限、工序、设备插件目录、设备插件唯一业务身份、客户端发布以及生产归档查询的业务来源，并负责创建设备插件、绑定其独立发布系列和生成完整安装内容。

Cloud 必须区分生产业务主链与安装运行视图：

```text
生产数据查询：工序 → 设备插件 → PLC 总览 → 单个 PLC 明细/数据
安装内容生成：选择一个或多个已绑定设备插件 → Cloud 自动匹配 Host 与完整运行闭包
运行状态查看：按客户端真实上报查看宿主、Host、Launcher 和已安装设备插件
```

- 设备插件就是一套具体现场设备业务。一个工序下有多个设备插件，就表示该工序下登记了多套具体设备业务。
- 生产查询按工序、设备插件和插件内部 PLC 定位数据；物理电脑、Host 和 Launcher 都不是生产数据分类节点。
- 一台物理电脑可以承载多个设备插件。Launcher 只是通用的启动、更新和状态入口，不生成“本机安装实例编号”，也不成为设备插件的业务身份。
- 设备插件换电脑或重新安装，只要 Cloud 没有删除它，就仍是原设备插件并沿用原 `ClientCode`；物理位置变化不新建设备身份。
- 设备插件 A、设备插件 B 等显示名称只能描述具体插件，不得成为 Cloud 通用框架中的固定分支；当前现场名称只在第 8 章解释。

## 2. 工序、设备插件、PLC 与生产查询

### 2.1 工序和设备插件目录

本节细化总纲 `BR-DOM-014`～`BR-DOM-019`、`BR-DOM-026`～`BR-DOM-027`、`BR-CLOUD-001`～`BR-CLOUD-003`、`BR-CLOUD-031`～`BR-CLOUD-032`。

- 工序由具有对应管理权限的真实角色在 Cloud 创建；未裁决为 `Admin` 专属前不得用未明确角色的泛称代替角色和权限点。工序分类码和 `supportedProcessType` 在保存、比较和建立唯一约束前必须移除全部 Unicode 空白字符并且不区分大小写，数据库保存值、唯一索引和所有业务校验统一使用同一个规范化结果；同一工序下的设备插件共享该分类，工序码不能承担设备插件唯一身份。
- Cloud 以通用主数据管理模切、匀浆及未来工序；一个工序可以登记任意数量的独立设备插件。
- 独立插件包发布系列必须先发布并验证，声明自己的 `supportedProcessType` 和隐藏 `ModuleId`；`supportedProcessType` 按上述工序码规则规范化，`ModuleId` 不得被解释为工序码或与其画等号。
- 创建设备插件时，具有设备创建权限的 `Admin` 选择所属工序、全局唯一名称和一个“已发布、已验证、尚未绑定”的插件系列；Cloud 在同一事务内校验工序码匹配、生成不可变的 `ClientCode` 和内部数据库主键、完成系列一对一绑定并记录审计。任一步失败都不得留下设备记录或半绑定关系。
- 插件系列发布、设备插件创建、任何获准的工序变更、活动 catalog 投影和安装内容生成都必须重新校验规范化工序码与 `supportedProcessType` 一致；不一致时拒绝进入下一状态，不能靠名称、`ModuleId` 或人工确认绕过。
- 一个设备插件代表一套具体现场设备业务。设备插件 A 和设备插件 B 必须创建为两个设备插件，并分别绑定自己的独立插件包发布系列；即使代码相似，也不能合并成一个包的两个运行实例。
- 同一工序下的插件可以有不同 PLC 数量、字段、完成条件和 MES 语义；Cloud 不得用统一工序模板覆盖插件自己的事实。
- 同一工序新增设备插件 C 或其它设备时，只新增一份独立业务文档、一个独立插件包发布系列、一个设备插件及其插件内配置，不修改 Cloud、Host、Launcher 或 AI 的通用判断；即使业务内容与现有插件重复，也不得共用业务正文。
- 显示名称用于人员识别且受唯一约束，`ClientCode` 用于稳定业务归属；任何一方都不得通过设备插件 A/B 等显示名称猜测另一个身份。

### 2.2 查询层级

本节细化总纲 `BR-CLOUD-016`～`BR-CLOUD-025`、`BR-PLUGIN-016`、`BR-DATA-015`～`BR-DATA-020`。

Cloud 面向人员和 AI 的生产数据查询遵循同一层级：

1. 选择工序；
2. 只展示该工序下的设备插件；
3. 选择设备插件后，默认展示该插件的 PLC 列表和状态总览；
4. 选择某个 PLC 后，展示该 PLC 的明细、状态和生产数据；只有人员明确选择跨 PLC 汇总时才执行汇总查询。

- 某个设备插件包含 12 个 PLC 时，选择该插件后应展示 12 个 PLC 数据分类；不能显示成 12 个插件或 12 台上位机。
- 查询某个插件不得混入同工序其它插件的数据；查询某个 PLC 不得混入其它 PLC 或其它插件的同名 PLC。
- 查询、分页、导出和汇总必须保留工序、插件、PLC 及授权范围；显示名称不得替代稳定过滤身份。
- PLC 清单、名称、地址和业务配置由设备插件自己的独立数据库及首次播种维护，Cloud 不创建、不修改，也不能从设备插件显示名称猜测数量或字段。
- PLC 状态权威链固定为“插件通过 SDK 提供完整快照 → Host/Edge 校验并上传 → Cloud 保存设备插件状态投影”。Cloud 页面和 AI 只读取该投影，Cloud 不直接调用插件、不连接插件数据库，也不在页面刷新时临时穿透到现场。
- 实时采集状态来自插件运行时缓存；PLC 地址等相对稳定配置从插件独立数据库加载到客户端缓存。配置修改必须完整执行 `BR-PLUGIN-009` 的“写前版本提升与失效 → 数据库提交和重载 → 写后再次失效并装载已提交值 → 拒绝旧并发回填”缓存双删/双杀；正常采集、状态查询和快照上传不得逐次查询插件数据库。
- Host/Edge 上传的快照结果只有完整权威的 `Authoritative` 或无法形成完整快照的 `Unavailable`。结果必须保留 `ClientCode`、PLC 身份、清单版本、采集时间和新鲜度；Cloud 不能用名称或物理宿主推断归属。
- 数据库读取失败、缓存异常、插件异常或链路失败时，不得把空数组作为 `Authoritative` 上报并清空 Cloud 投影；必须发布 `Unavailable`，Cloud 保留上一份投影且明确标记为历史/过期并显示采集时间。
- Human 上位机 PLC 总览必须在每次查询时按投影接收时间和 Cloud 统一配置的新鲜度窗口重新裁决有效状态；默认窗口 3 分钟，恰好 3 分钟仍有效，只有 `age > window` 才过期。过期后即使最后一次原始值为 `Connected`，也不得继续显示在线，必须显示过期/不可用并保留最后采集时间。Human、AiRead 和动态元数据必须调用同一 resolver，不得各自维护阈值或算法。
- 只有 Host/Edge 明确上报 `Authoritative` 的零 PLC 清单，同时携带高于上一份投影的新清单版本和明确清空意图时，Cloud 才能把 PLC 投影清为零。普通空数组、旧版本、缺少清空意图或来源不完整都必须拒绝，不能把异常误判成现场真的没有 PLC。
- 上述 PLC 状态投影只服务 PLC 列表、地址和状态展示；历史生产数据查询仍在 Cloud 归档数据中执行，不能拿运行快照或状态投影冒充生产查询结果。
- 空结果只表示当前授权和筛选范围没有数据，不能生成模拟值、借用其它插件数据或吞掉加载错误。

## 3. 设备插件下载、技术注入与客户端发布

本章细化总纲 `BR-DOM-025`～`BR-DOM-027`、`BR-CLOUD-004`～`BR-CLOUD-015`、`BR-CLOUD-031`～`BR-CLOUD-035`、`BR-EDGE-021`～`BR-EDGE-023`；上位机只是安装运行视图，不是下载前置身份。

### 3.1 发布系列、创建设备绑定和下载选择

Cloud 的业务顺序固定如下：

1. 具有工序管理权限的真实角色先创建或选择已经具有规范化工序码的工序；
2. 有发布权限的人员发布一条带独立业务文档、`supportedProcessType`、隐藏 `ModuleId`、Profile、加载入口和兼容声明的独立插件包系列；发布验证通过后，该系列先进入“已发布、未绑定”候选集合；
3. 创建设备插件时，具有设备创建权限的 `Admin` 只填写全局唯一名称、选择工序，并从候选集合选择一个工序匹配的未绑定系列；
4. Cloud 在一个事务内重新校验系列仍未绑定、工序码与 `supportedProcessType` 一致、`ModuleId` 技术唯一，生成唯一 `ClientCode` 和内部 `DeviceId`，完成设备插件与发布系列一对一绑定并写入审计；任一步失败整次回滚；
5. 下载页面按工序展示已经完成绑定且存在可分发版本的设备插件；人员只选择需要安装的一个或多个设备插件，不再分别选择“插件包＋设备”并自由拼接；
6. Cloud 重新校验各设备插件、系列、工序和活动 catalog 后，固定自动解析真实插件版本、唯一 Host 结果及完整运行闭包，全部通过才生成安装内容。

- 一次下载可以选择同一工序下的设备插件 A、设备插件 B，或跨工序选择多个设备插件；生成内容必须继续保持每个插件包、身份、配置、目录和启动边界独立。
- 独立发布系列绑定后只服务该设备插件；后续版本继续发布到原系列，不能把同一系列再绑定第二个设备插件，也不能通过下载或更新动作把设备插件切换到另一系列。
- 设备插件不存在有效一对一绑定、工序不匹配、所选组合发生 `ModuleId` 技术冲突、没有可分发真实版本、版本不兼容、依赖不完整或凭据无法安全生成时，Cloud 必须阻止生成并指出缺失项，不能生成一个客户端打开后才发现缺 DLL 或运行时的残缺安装包。
- Host 不是人员在业务表单中维护的第二身份。Cloud 只能从已批准的 `stable/win-x64` Host 中，自动选择所有已选设备插件共同兼容的最高版本；选择结果必须唯一，候选不存在或最高结果不唯一都直接阻断。
- 下载页面和确认弹窗只读展示系统选定 Host 的版本、通道、架构、目标框架（TFM）、摘要/hash 及选择依据。人员不得人工改选、降级或用请求参数覆盖 Host；需要其它 Host 时只能先修正正式兼容声明或发布事实，再重新生成。
- Launcher 只是安装后发现、启动和更新设备插件的通用工具。Cloud 不为物理电脑或 Launcher 生成“本机安装实例编号”，也不要求下载前先把设备插件绑定到某台电脑。
- 设备插件换电脑或重新安装时，从 Cloud 重新选择原设备插件生成安装内容，继续使用原 `ClientCode`；不能因为宿主变化自动创建一台“新设备”。
- 安装内容生成、下载、安装中和 `Pending` 安装交付状态都不得创建、替换或重新决定设备插件与发布系列的业务绑定；重新安装必须继续解析创建事务已经确定的原绑定。这里的安装交付状态不等于第 3.4 节短期凭证的有效性状态。

### 3.2 当前生产存量绑定迁移

本节只处理当前生产中已经存在设备插件、安装和运行事实，但缺少“设备插件 ↔ 独立发布系列”绑定记录的存量迁移，继承 `BR-CURRENT-011`、`BR-CURRENT-012`，不得推广成日常创建捷径。

- 补绑定前必须同时取得并交叉核对四类生产证据：Cloud 现存 Device/`ClientCode`、不可变安装 Binding、运行心跳实际使用的 Profile，以及已发布 manifest 与精确插件版本。
- 只有四类证据对同一个设备插件、`ClientCode`、Profile、模块入口、发布系列和精确版本形成唯一且相互一致的闭环，才允许补写缺失绑定；补写不得轮换 `ClientCode`、替换设备身份、重发凭证或把安装/在线状态当成绑定依据。
- 任一证据缺失、候选不唯一或互相冲突时，必须停止并保留审计，不得按显示名称、当前现场简称、MES 身份、`ProcessType` 或物理电脑位置猜测。
- 如果证据证明现有设备插件归属了错误工序，必须由 `Admin` 明确选择已有正确工序，或先创建正确工序，再以受控事务按“移除全部 Unicode 空白字符且不区分大小写”的统一规范值调整 `ProcessType` 并记录调整前后事实；调整后必须重新通过上述四证核验，才能补写绑定。

### 3.3 首次安装技术配置与完整运行闭包

- Cloud 只在生成首次安装或重新安装内容时，按所选设备插件分别写入完整技术配置：该插件的 `ClientCode`、Cloud/bootstrap 与更新链路、获准下发的凭据材料、插件加载路由、Profile、包及版本校验信息、隔离目录和运行所需的通用技术参数。
- Cloud 不向插件注入 PLC 清单、PLC 地址、点位、MES 身份、MES 地址、业务播种、完成条件或业务 Schema。上述内容全部属于插件自己的业务实现、独立数据库和首次安装播种；后续业务配置只能在插件客户端本地修改，Cloud 只读查询，不远程改写。
- 插件只在自己的独立数据库首次创建且尚未初始化时执行一次自身播种；普通启动、重启或升级不得重复播种、重置或覆盖现场配置。Cloud 既不执行该播种，也不把播种数据打进技术注入配置。
- 首次下载和重新安装必须逐项满足总纲 `BR-CLOUD-007` 定义的唯一完整离线闭包不可缺项清单；本文及任何项目级示例都不得删减、概括替代或把其中某一项降为可选。Schema、页面路由、插件入口和首次播种定义属于各插件的安装产物，不因此变成 Cloud 可修改的业务配置。
- Cloud 生成前必须核对 `BR-CLOUD-007` 每一项真实存在、版本及 TFM 相容且 hash/大小与 catalog 一致；任一项缺失或校验不一致都必须在切换为可用版本和暴露启动项前阻断，禁止用空文件、临时占位、现场联网补齐、系统碰巧预装、运行时猜测或忽略错误来“完成”生成。
- 同一次下载中的多个设备插件不得共享可变业务配置、凭据、数据目录、日志、缓存或 Profile。公共 Host/SDK 可以复用，但不能因此合并设备插件包或 `ClientCode`。
- 重新下载可以按当时有效的技术配置重新生成完整安装内容，但不得新建设备身份。凭据签发、轮换、失效和重装恢复的精确协议由专题契约定义；任何情况下都不能把凭据明文写入日志、页面或另一个插件的配置。

### 3.4 版本化 Binding、Pending 凭证和独立激活

- 安装 Binding Schema 必须具有明确版本。Cloud 生成器、Installer、Launcher 和校验器必须在同一批次认识同一版本、每个 `ClientCode` 的必填技术字段、签名与完整性规则；任一环节不认识当前版本、缺少字段或验签失败，都必须阻断该安装内容进入可用状态。
- Cloud 是 Binding v3 wire schema owner，唯一 `EdgeBindingWireSchema` 必须同时驱动 17/17 路由的生成字节、计划指纹、签名载荷和重下载对账。完整字段—运行配置键—路由表只在[Edge 宿主插件分发契约第 5 章](../../IIoT.EdgeClient/docs/Edge客户端宿主插件分发契约.md#5-binding-v3-和凭证)定义；Cloud 不得维护第二份子集、旧别名或不同占位符规则。
- 每个所选 `ClientCode` 可以在受签名清单保护的安装载荷中携带一份默认 7 天有效的短期 `Pending` bootstrap 原凭证。凭证逐设备插件绑定和校验，不能把设备插件 A 的凭证复用于设备插件 B，也不能用一个全局凭证代表整个安装组合。
- Cloud 生成或凭证校验任一步失败时，不得发布半成品，也不得覆盖该设备插件已有有效凭证；同一安装组合中的其它 `ClientCode` 也不得因此丢失或更换已有凭证。
- `Pending` 过期只拒绝该 `ClientCode` 后续使用这份短期原凭证执行新的 bootstrap；它不撤销该设备插件已经成功激活的运行凭证，也不改变同一安装组合中其它设备插件的凭证状态。
- Installer 验证载荷后，必须把每个 `ClientCode` 的原凭证导入实际运行 Launcher 所使用的操作系统 Credential Manager，再生成不包含凭证原文的运行时 Binding 引用。原凭证不得原样写入正式安装目录、Profile、共享 `host.db`、日志或恢复文件。
- Credential Manager 只降低普通配置文件、备份和离线复制泄漏风险，不能防止同一 Windows 登录账户下的恶意进程、Windows Local Administrators 组成员或进程内存读取；本边界不得被宣传成设备凭证在本机绝对不可提取。
- 共享宿主、全部所选插件文件、Profile 和非凭证 Binding 素材必须整组原子安装；文件组不完整时不得暴露任何新启动项，并保留上一可用文件组与已有凭证。
- 每个设备插件在该 `ClientCode` 第一次真实 `ready` 后，独立把自己的 `Pending` 凭证激活为运行凭证，并且只撤销同一 `ClientCode` 的旧 refresh 凭证。设备插件 A 是否 ready 不等待设备插件 B；任一设备未 ready、安装失败或激活失败，都不得改变其它设备插件的启动资格或凭证状态。
- Binding 字段、Schema 版本号、清单布局、签名算法、Credential Manager 键名、`ready` 判定和激活接口等精确协议继续由客户端分发及凭证专题契约承载，本文不复制 DTO 或文件格式。

### 3.5 发布、安装和运行状态

- 每个设备插件拥有自己的独立插件包发布系列；Host、设备插件包及各自版本都是不同发布对象，正式版本、hash、大小、下载地址和发布说明只能来自受控真实产物。
- “设备插件已创建”“发布系列已绑定”“版本已发布”“安装内容已生成”“文件已下载”“客户端已安装”“插件正在运行”“存在可用更新”是不同事实，不能互相推断或用前一个状态冒充后一个状态。
- Cloud 只有收到客户端对该设备插件的真实安装或运行上报后，才能展示对应状态；生成或下载成功本身不能标记为已安装、在线或运行。
- 版本上报只说明安装版本，运行心跳只说明插件运行新鲜度，PLC 状态只说明对应 PLC 的实时情况；任何一类都不能替代另一类。
- 上位机管理页面可以按客户端真实上报展示物理宿主信息、Host/Launcher 版本、已安装设备插件及更新状态，但这些都是运行投影，不参与 `ClientCode` 唯一性，也不改变设备插件归属。
- 发布、归档、保留和永久删除必须保持真实产物、状态、在用事实、原因和审计一致；精确 DTO、接口、事务、文件布局与恢复算法不在业务规则中展开。

## 4. 身份、人员与权限

### 4.1 Cloud 设备业务身份

本节细化总纲 `BR-DOM-014`～`BR-DOM-019`、`BR-DOM-025`～`BR-DOM-027`。

- **设备插件就是设备维度。**一个设备插件代表一套具体现场设备业务，不再额外创建一个与插件并行、要求人员维护的“Cloud 设备身份”。
- `ClientCode` 是设备插件唯一业务身份，由 Cloud 在创建设备插件时自动生成、全局唯一且不可由人员修改。bootstrap、上传归属、授权范围、归档、安装配置和重装恢复都必须回到同一个 `ClientCode`。
- `DeviceId` 只作为 Cloud 数据库内部主键，由数据库和 Cloud 自动维护。它可以用于内部关联和性能实现，但不能成为第二个业务唯一键，不能要求人员选择或维护，也不能取代 `ClientCode` 出现在跨端业务口径中。
- `ModuleId` 只能是系统从插件发布事实维护的隐藏技术加载字段。它不显示在业务表单中，不参与业务选择、授权或归档，也不得要求人员同时维护 `ClientCode` 和 `ModuleId`；但为避免加载歧义，它在活动发布目录和同一安装组合内必须保持技术唯一，冲突时阻止发布、绑定或生成安装内容。
- `ProcessType` 只表示工序分类码。它与插件系列的 `supportedProcessType` 在保存、比较和建立唯一约束前都必须移除全部 Unicode 空白字符（无论位于开头、中间或结尾）并且不区分大小写，数据库保存值、唯一索引和所有业务校验必须使用同一个规范化结果。同一工序下的设备插件 A、设备插件 B 可以具有相同工序码；两种工序码字段都不能标识设备插件，更不得与 `ModuleId` 画等号。
- `TypeKey` 只表示设备绑定插件版本声明的业务记录类别；一个插件版本可以声明多项，每项拥有独立 Schema、查询模式和公开字段。Cloud 上传、幂等、存储和查询必须使用 `DeviceId/ClientCode + TypeKey` 验证能力，不能把 `ProcessType`、`TypeKey` 与 `ModuleId` 混同。
- 设备插件显示名称面向人员且不允许重复，但稳定业务归属仍以 `ClientCode` 为准；名称修改不得产生新设备身份。
- 物理电脑、Host 和 Launcher 都是运行载体或通用组件，不是设备插件身份。换电脑、重装、Host 升级或 Launcher 更新不得改变 `ClientCode`。
- MES 的上位机编码、站号、签名 Token 和业务回执由插件自己的配置与通道管理，并与 Cloud 的内部 `DeviceId`、bootstrap、Access/Refresh Token、会话和门控完全分离；`ClientCode` 只可随 `CompletionId + TypeKey` 作为同一完成事实交给 MES，不得被解释为 MES 凭据或共享会话。

### 4.2 人员、账号和授权

- 人员档案和身份账号使用同一非空业务身份；停用、终止或访问权变化必须使旧授权失效，不得只靠页面隐藏。
- “管理员”只表示真实 `Admin` 角色；`DeviceAdmin`（运维员）、`HrAdmin`（人事管理员）、`RoleAdmin`（角色管理员）等均是独立角色。系统可以存在多个经授权的 `Admin`，不得给 `Admin` 添加不存在的等级前缀，也不得用唯一账号口径替代真实角色关系。
- 人员可以先入职再分配业务对象；操作插件或设备必须同时满足对象分配和功能权限。
- 人员设备范围按明确的设备插件 `ClientCode` 集合授权，不因获得某个工序而自动继承该工序下全部插件或 PLC。
- 人类用户、Edge 设备、AI 服务账号和机器发布身份必须保持不同 actor 边界；机器身份不得借字符串角色进入 Human Admin 通道。
- 角色、个人特批、启停、密码、设备范围和高风险操作走各自权限与审计边界；页面能力不能代替服务端授权。
- 权限目录只能接受正式已知权限；未知、空白、禁止或越权输入应整次拒绝，不能静默丢弃后部分成功。

### 4.3 当前权限产品策略

以下是现有 Cloud 权限业务的待复审细化，不定义 Handler、数据库锁、JWT 或接口实现：

- `Admin` 是受保护的真实角色而不是唯一账号。本批“支持多个 `Admin`”只指数据库不变量、迁移预检和空库播种对多成员兼容；未新增或开放 `Admin` 成员增删产品接口，该产品能力仍需单独复审。Cloud 工号 `101650` 是规范的 Cloud 绑定 AI `Admin`，但不是系统唯一 `Admin`。
- 常用岗位优先使用内置角色模板：`DeviceAdmin`、`ClientInstallerOperator`、`ClientReleaseManager`、`ProductionViewer`、`RoleAdmin`、`HrAdmin`，不能靠逐账号复制权限代替岗位模型。
- `ProductionViewer` 只读取设备、客户端发布和上位机/PLC 状态，不在 Cloud 修改、启停或删除现场 PLC。
- 员工资料、访问权、启停、角色、密码、对象范围和个人特批是不同业务动作，必须分别授权和审计，不能通过“修改资料”夹带其它变化。
- `RoleAdmin` 只维护非 Admin 角色；角色治理权限不得扩散到普通角色。个人特批是 Admin 专属例外，常规岗位优先通过角色模板解决。
- `HrAdmin` 可以维护普通人员资料、非 Admin 角色、对象范围和启停状态；不得维护个人特批、重置密码、永久终止人员或操作 Admin。
- 人员对象范围以明确的设备插件 `ClientCode` 集合授权，不因获得某个工序而自动继承该工序下全部设备插件或 PLC；物理上位机信息不扩大对象范围。
- 普通人员不得修改自己的角色或扩大自己的对象范围。真实角色变化、停用、重新启用和永久终止必须使旧 Human 会话失效，重新启用后也不能复活旧凭据。
- 人类登录执行失败计数和锁定；密码错误、账号不存在、停用和锁定对外使用统一失败语义。`Admin` 重置密码不自动解除锁定，除非另有已复审的解锁动作。
- 客户端发布权限与设备管理权限分离；查看、生成安装内容、发布和管理/硬删除是不同权限。机器发布身份只获得完成发布所需的最小权限，不得进入 Human Admin 通道或获得设备管理能力。
- 所有成功或失败的越权、角色、对象范围、个人特批、密码和高风险操作都必须形成结构化脱敏审计。

## 5. 配方

本章只承接总纲 `BR-CLOUD-028` 的冻结结论。

- 配方从当前裁决开始冻结，不再新增或扩展；冻结不要求删除已经存在的数据库、接口、页面、权限或审计，也不要求关闭已有 CRUD。
- 已有实现继续保留只表示历史能力存在，不代表配方已经接入、批准进入或实际参与生产流程。
- 本轮不为配方补造归属关系、状态机、权限、接口或客户端消费行为，也不把配方绑定到工序、设备插件、PLC 或其组合。
- 将来现场提出明确配方需求时，必须单独完成业务复审和跨端设计后再解除冻结；在此之前，配方不得作为其它功能的生产前置条件。

## 6. 真实数据、归档、删除与审计

### 6.1 生产归档

- Cloud 只归档插件上传的真实完成事实，不负责判断前后工序、生产放行或 MES 放行。
- 每条生产记录必须能够定位所属工序、插件和 PLC；不能只用工序名称混合归档同工序全部插件。
- 插件数据使用公共检索字段和插件 Schema 描述的业务字段；不同插件可以拥有不同 Schema。
- 未知字段、非法类型、范围或枚举必须明确拒绝；不能静默丢弃，也不能用默认假值补齐。
- 上传“已接受”、异步消费完成、最终落库和查询可见是不同状态，不得用前一状态冒充后一状态。
- 生产记录和产量只能来自插件定义的真实完成事实；PLC 当前值、连接状态、仅入队成功以及 Cloud/MES 上传成败不能生成产量。
- Cloud 与 MES 是两条独立上传链；Cloud 成功不能证明 MES 成功，MES 成功不能证明 Cloud 成功。
- 产能、生产记录、客户端版本、运行心跳、PLC 状态和设备日志是不同事实源，只能在明确业务口径下关联查询，不得互相补数或推断。

### 6.2 查询、归档和设备插件删除

设备插件误发清理细化总纲 `BR-CLOUD-029`、`BR-CLOUD-030`。

- 历史生产数据、产能和日志以 Cloud 正式归档为查询来源，并同时应用功能权限和对象范围。
- 生产记录默认不可修改、不可删除；确需更正或删除时，只允许真实 Human Admin 对明确记录执行，必须给出原因、二次确认并保存修改前后事实或删除前快照。
- `Admin` 可以直接永久级联删除一个明确设备插件及其关联数据；是否存在安装/运行事实、生产记录、过站记录、产能、日志、授权、会话、`Pending` 凭证、客户端状态、PLC 投影、绑定或其它依赖，不得成为删除阻断条件。
- 级联删除必须在一个原子事务中完成；任一关联数据清理失败都必须整体回滚，不得把部分数据库或文件处理报告为成功。
- 每次设备插件删除必须记录结构化审计；影响预览、删除原因和二次确认不是当前强制前置条件。实现可以提供辅助提示，但不得把它们升级为拒绝删除的业务门禁。
- Human 设备台账中具备删除能力的 `Admin` 对明确设备执行直接删除；页面不得自动请求影响预览、打开删除确认框或要求输入设备名、确认文本或原因。删除失败时保留当前选择与详情，成功时清理该设备页面状态并刷新列表。
- 不可变审计及安装生成证据继续保留；设备插件删除后不得继续出现在工序选择、下载选择或活动 catalog 中，相关活动密钥和会话必须失效。历史证据留存不等于业务对象仍可使用。
- 本删除规则只处理设备插件级联删除，不改变上一条“单条生产记录纠错”的独立 Human `Admin` 规则，也不凭空增加“卸载”“解绑”或“迁移成新设备”等业务状态。

## 7. AI 只读业务边界

- Cloud 是 AICopilot 当前真实制造业务数据的权威来源；AICopilot 对 Cloud 保持严格只读。
- AI 查询与 Human 查询使用同一“工序 → 设备插件 → PLC 总览 → 单个 PLC 明细/数据”业务层级，并从 Cloud 动态读取工序、设备插件、PLC 和 Schema。
- Human 与 AiRead 使用共享的底层只读元数据服务但保留独立权限入口；Human 可按工序枚举设备、按设备枚举 PLC 和 `TypeKey`/Schema，AiRead 提供受限的设备 PLC 与数据 Schema 端点。实际安装插件版本或能力缺失、PLC 状态不可用/过期时必须明确返回不可用，不能冒充空清单。
- 工序下插件不唯一、插件内 PLC 范围不明确或其它条件不足时，AI 必须继续确认，不能选择第一条或使用名称猜测。
- AI 不得把任何当前现场简称、线别、极性或显示名称硬编码到插件身份、PLC、字段或接口的映射。
- 交互式 AI 查询只允许在当前 Cloud 用户的有效委托身份、权限和对象范围内读取；委托缺失、过期、撤销、无效或主体不匹配时直接拒绝，禁止解释为 `Global` 或无范围过滤。
- 静态系统 Token 不得代替当前用户执行交互式读取。明确的非交互系统任务如需系统身份，必须使用与用户委托物理分离的认证、最小范围和审计，不得由用户请求自动降级或切换过去。
- AI、MCP、Tool、Text-to-SQL 和 Human-in-the-loop 均不得创建、修改、删除、补录、审批、派发或触发 Cloud 制造业务流程。
- typed AiRead 保留并执行当前用户委托；真实 Cloud Direct DB 与 Text-to-SQL 当前整体关闭。只有委托范围贯穿 SQL，且 AST 强制行条件或数据库 RLS 能独立证明范围后，才允许另行复审开放。
- typed provider、查询参数、DTO、限流、审计和跨仓验收的精确技术语义只由 [AI 只读接口契约](AI只读接口契约.md) 和 AICopilot 对应专题契约定义。

## 8. 当前 AP/CP 现场事实

本章只承接 `BR-CURRENT-*`，不能用于推导未来框架。

- 当前私有模切设备插件为 AP（P1 线负极模切）和 CP（P2 线正极模切）；它们是当前两个独立插件，不是 Cloud 永久工序枚举。
- 当前 CP 与 AP 是两个设备插件，分别具有自己的 `ClientCode`、独立插件包和发布系列；不能因都属于模切而合并身份或安装包。
- 当前正极模切插件配置 12 个 PLC，Cloud 查询必须在该插件下面保留 12 个 PLC 分类。
- 当前 AP/CP 各自维护 PLC 清单、点位、MG1/MG2、完成事实、MES 配置和 Schema；这些细节只约束对应插件。
- 当前 CP/AP 的 MES `upperComputerNo` 为 `P2-CPUC`、`P1-APUC`，只来自插件配置，不能作为 Cloud 身份。
- 当前 AP/CP 插件和 Host 版本事实以真实发布 catalog、产物与部署证据为准；本文不把声明版本冒充已安装版本。
- 当前生产若缺少“设备插件 ↔ 独立发布系列”绑定，只能按第 3.2 节和 `BR-CURRENT-011`、`BR-CURRENT-012` 的四证闭环补写；缺失、候选不唯一或冲突时停止，不得按当前 AP/CP 名称或其它业务标签猜测。
- `R100` 当前冻结，不属于已启用设备工况；在取得正式 PLC 资料并经用户单独确认前，Cloud 不得展示、查询或推断该候选点位。
- 当前实例的业务细节分别由 [AP 插件业务规则](../../IIoT.Edge.Plugins.Private/docs/AP插件业务规则.md) 和 [CP 插件业务规则](../../IIoT.Edge.Plugins.Private/docs/CP插件业务规则.md) 独立承载；即使内容重复也不得合并成一份共享业务正文，其中任何固定值都不得提升为 Cloud 通用框架规则。
